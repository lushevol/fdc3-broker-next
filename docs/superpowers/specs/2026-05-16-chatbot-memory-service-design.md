# Chatbot Memory Service Design

## Goal

Build a standalone SQL-backed memory service for the chatbot so financial markets operators can persist BAU work patterns, preferences, instructions, watchlists, and operational notes across sessions without storing full chat transcripts as long-term memory.

## Context

`services/chatbot-backend` currently wires `AutoMemoryTools` through `MemoryToolsFactory`. That stores per-user Markdown memory files under `./data/memories` and injects memory tools into the agent flow. Conversation history remains request-scoped or in process. This design replaces file-backed long-term memory with a standalone service that owns persistence, schema migrations, and administrative extension points.

## Scope

The POC stores durable operator memory:

- Preferences: response style, default markets, formatting, language, risk tolerance for proposed actions.
- BAU workflows: repeated task patterns, runbooks, daily checks, escalation habits.
- Watchlists: instruments, clients, books, desks, regions, dashboards, or recurring market contexts.
- Instructions: user-approved standing instructions for the assistant.
- Notes: explicit user or admin notes that should be recalled later.

The POC does not store full chat transcripts, raw tool outputs, market data snapshots, or regulated records of operator decisions. Those need separate retention, audit, and compliance design.

## Architecture

Add `services/memory-service`, a standalone Spring Boot service with Spring Web MVC, Spring Data JPA, Flyway, Actuator, SQLite for local POC, and PostgreSQL-ready configuration. `chatbot-backend` talks to it through a typed `MemoryClient` and exposes memory to the model through tool callbacks and a compact context block.

The service owns its database schema and migration history. `chatbot-backend` depends only on API DTOs and does not import memory persistence entities.

```
chatbot-backend
  ├─ MemoryClient
  ├─ MemoryToolCallbackFactory
  └─ AgentService prompt/tool integration
        │ REST
        ▼
memory-service
  ├─ MemoryController
  ├─ MemoryApplicationService
  ├─ MemoryRepository
  ├─ Flyway migrations
  └─ SQLite now / PostgreSQL later
```

## Data Model

Primary table: `memory_entries`.

Required columns:

- `id`: UUID string generated by the service.
- `tenant_id`: tenant or environment boundary. Defaults to `default` for local POC.
- `user_id`: operator identity. Required.
- `desk`: optional desk or business group.
- `type`: `PREFERENCE`, `BAU_WORKFLOW`, `WATCHLIST`, `MARKET_CONTEXT`, `INSTRUCTION`, `NOTE`.
- `title`: short human-readable label.
- `body`: memory body.
- `tags_json`: JSON array encoded as text for SQLite compatibility.
- `source`: `USER`, `ASSISTANT_CONFIRMED`, `ADMIN`.
- `confidence`: decimal from `0.0` to `1.0`; explicit user/admin memories default to `1.0`.
- `status`: `ACTIVE`, `ARCHIVED`, `DELETED`.
- `schema_version`: integer set by the application. Starts at `1`.
- `attributes_json`: JSON object encoded as text for optional future metadata.
- `created_at`, `updated_at`, `last_used_at`: UTC timestamps.

Indexes:

- `(tenant_id, user_id, status, updated_at)`
- `(tenant_id, user_id, type, status)`
- `(tenant_id, user_id, desk, status)`

## Schema Evolution

Schema changes are managed with Flyway migrations only. JPA DDL auto-generation is disabled outside tests. Each migration is append-only and named with the repo's existing convention adapted for the service, for example `V1_0_0__memory_schema_init.sql`.

The model deliberately includes `schema_version` and `attributes_json`:

- `schema_version` lets application code distinguish older records if a future migration changes meaning rather than just structure.
- `attributes_json` holds low-risk extension metadata, such as `assetClass`, `region`, `workflowFrequency`, or `sourceConversationId`, without requiring an immediate table change.
- Core query fields remain columns. Do not hide fields needed for filtering, retention, or access control inside JSON.

PostgreSQL migration later should add native JSONB only after the service is stable. Until then, keep JSON as text plus Jackson validation so SQLite and PostgreSQL behavior stays aligned.

## API

Initial REST API:

- `POST /api/memory/entries`: create an entry.
- `GET /api/memory/entries`: search entries by `tenantId`, `userId`, optional `desk`, `type`, `q`, `tags`, `status`, `limit`.
- `GET /api/memory/entries/{id}`: fetch one entry by id within caller scope.
- `PATCH /api/memory/entries/{id}`: update mutable fields.
- `POST /api/memory/entries/{id}/archive`: mark an active memory archived.
- `DELETE /api/memory/entries/{id}`: soft-delete a memory.
- `GET /actuator/health`: service health.

All read and write operations require scope fields. The POC may accept scope fields from request parameters or headers, but controller code must centralize scope resolution so authentication can replace it later.

## Chatbot Integration

`chatbot-backend` adds:

- `MemoryServiceProperties` for `enabled`, `baseUrl`, `tenantId`, `requestTimeout`.
- `MemoryClient` for REST calls.
- `MemoryToolCallbackFactory` exposing model tools:
  - `MemorySearch`
  - `MemoryCreate`
  - `MemoryUpdate`
  - `MemoryArchive`
- Prompt context builder that retrieves top active memories for the operator and injects a compact "Operator memory" system section.

The assistant should persist a memory only when the user explicitly asks, confirms, or the interaction is clearly a preference/standing instruction. No automatic transcript scraping in the POC.

## Error Handling

If `memory-service` is unavailable, `chatbot-backend` continues without long-term memory and logs a structured warning with `conversationId`, `userId`, and failure category. Memory failures must not fail normal chat unless the current user explicitly invoked a memory management action.

The memory service returns validation errors as HTTP 400 with machine-readable field errors, missing entries as 404, and unexpected failures as 500.

## Observability

`memory-service` exposes Actuator health. Service methods and controller endpoints should log structured events for create, update, archive, delete, and failed validation. `chatbot-backend` should add counters for memory context lookup success/failure and memory tool execution success/failure.

## Testing

Use TDD.

- `memory-service` controller tests validate request/response shape and scope filtering.
- Service tests validate required fields, soft delete, archive, search, tags, and schema-version defaults.
- Repository integration tests run against SQLite.
- `chatbot-backend` client tests use a mock HTTP server or mocked exchange function.
- Agent tests verify memory context is included when available and omitted when the service fails.

## Migration Path To PostgreSQL

PostgreSQL support is a profile and dependency change, not a rewrite:

- Keep repository code on JPA derived queries or portable JPQL.
- Keep migrations portable where possible.
- Store JSON as text during the POC.
- Add `application-postgres.yml` with a PostgreSQL datasource.
- Add PostgreSQL driver and Flyway PostgreSQL database support.
- Run the same service-level tests with PostgreSQL Testcontainers in a later hardening phase.
