# Process API Generation

Your Contract First Process API has been generated. An `/api` folder has also been provided.

## Tech Stack

The project was generated with Java 17 Quarkus Reactive.

## /api folder

- The `/api` folder consists of 2 files:
  - `/api/api-manifest.yml`- API Manifests will be used as declarative config of the final state of the API configurations which are to be applied as deployment time. The API Manifest is a yaml file which captures the Application API meta data and attributes required to provision the exposure of the API in SCB. This manifest will be used as input for API Gateway configuration(TBD), API Registry , API documentation and Security(TBD) configuration.
    = `/api/openapi.json`- The Open API Spec file that you provided when running sc-devkit.

## How the devkit works

- To generate your project, a maven plugin for generating code from `openapi-generator` has been used.

  - We read your openapi spec provided, then use it to generate Interfaces and Models based on the specification.
  - Files will be generated into the following packages: `main/com.sc.api.generated` and `test/com.sc.api.generated`
    - The `main/api` package will contain interfaces - specifying the list of paths as well as the Response types that the developer has to implement.
    - The `main/models` package will contain models - specifying the schema of the various Objects.
      - We use Java `record` type (introduced in JDK 14) to ensure immutability of model objects
    - The `main/providers` package contain various date time utilities needed for the project to compile when working with dates.
    - The `test/` package contains a unit test that you have to pass, it checks for the interfaces in the generated package, and requires that create at least 1 implementation of each interface.
  - Developers **should not touch the generated code**, and use the interfaces and models to satisfy the contract as specified in the open API specification.
  - Metadata about the command is also generated in `.scdevkit/answers.xml`.
  - Other static files will also be generated such as a basic `azure-pipelines-maven.yml` and `.gitignore`.

- To maintain sync between spec and code, we use 2 methods to ensure the sync between code and spec is established:

  - The first method is to **verify the integrity of generated code**:
    - By using the devkit, you can use the `Update -> Generic -> API - Java Quarkus Process API(OpenAPI/Contract-first) -> Dry-Run / Test` option to check if your code is currently in sync.
    - We compare the contents of the files present in the generated pkg -> sc.com.api.generated, with a tmp generated set of files generated by the project OAS.
    - If a diff occurs, we can assert at compile time that the code does not match the spec. (ie the tmp generated code from the spec does not match the code in the current repository)
  - We also check whether the code is correctly implementing the generated interfaces.
    - There is a Java Reflections package, that can inspect contents in a package.
      - We can check if there at least exist one class that implement this interface
      - If at least one class exist, then it means that an actual `Controller/Resource` is being exposed, since all annotations in the interface will be inherited by the child implementation, ie. the `@Path` annotation will be exposed in a quarkus app and thus the REST app is exposing the path as an interface for clients to connect to.

- To resync the project: you can use `Update -> Generate -> API - Java Quarkus Process API(OpenAPI/Contract-first) -> Resync` option to resync the generated code.
  - Your generated package will be wiped and regenerated using your latest Open API Specification. Thus, developers will have the latest interfaces and models that they need to write your contract-first API.

### Specifying custom @JsonProperty mappings

In order to facilitate the usage of `@JsonProperty` annotations, we have added a way to inject these annotations, so that the generated code will be populated when the project is generated or resynced.

#### Usage

In your open API spec, for the field that you want to inject the annotation, set the `x-field-json-property` property:

```json
{
  "accountNumber": {
    "type": "string",
    "description": "The account number",
    "example": "183512176",
    "x-field-json-property": "account_number"
  }
}
```

The field will then be generated with a `@JsonProperty` annotation.

# Development

## Implementing Interfaces

Please maintain at least one implementation of each interface within a seperate package - don't put the implementation code into the `com.sc.api.generated` package as it will be wiped when resyncing or regenerating. 

Create a seperate package like `sc.com.casa.api` and maintain the implementation there.

### Note that you don't have to add the annotations as annotation will be inherited by the implementing class.

```java
package com.sc.casa.api;

// Some other imports here
import org.jboss.resteasy.reactive.RestResponse;
import org.jboss.resteasy.reactive.RestResponse.ResponseBuilder;
import com.sc.api.generated.model.BulkAccountDetails; // Import the Model classes from the `generated` package.

public class AccountsApiImpl implements AccountsApi {

    @Override
    public RestResponse<BulkAccountDetails> getAccountDetailsByGroupId(AccountType accountType, AccountStatus accountStatus, Integer page, Integer size) {
        return ResponseBuilder
                .ok(new BulkAccountDetails())
                .build();
    }

}
```

## Enable lombok annotation processing

Make sure you enable lombok annotation processing so that the code can compile with intelliJ when using annotations such as `@Builder` and `@Getter`. Download the lombok plugin and use it.

## Running the application

Add a maven runtime configuration - `mvn quarkus:dev`, the REST Application should be up and running.

## Best practices

1. You should regularly check if your code is synced to your open API spec, use the `sc-devkit's` dry-run and sync option to test and sync your code to your spec.
2. Spec should be regularly updated if the interface of the API has changed, or the schema or the responses have changed, use the devkit to resync your code after the spec has changed.
