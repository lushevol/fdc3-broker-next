# EMS3 integration reference

Research date: 2026-09-27. Scope: the checked-in `new-auth-service` implementation and its supplied EMS3 samples. This is evidence about this squad's integration, not a verified EMS3 API specification or confirmation of production behavior. Hosts, credentials, and personal identifiers are deliberately omitted.

Planning update, 2026-10-02: the user confirmed that FlowZero is the only EMS3 pilot. Other application names appearing in the sample file are API examples, not evidence of completed onboarding. The [all-application migration plan](../../../../services/single-ui-bff-ems3/docs/ems3-migration-plan.md) includes creating their EMS3 definitions, user assignments and comparison results as migration work.

## What this service demonstrates

The service obtains an application access token, downloads entitlement membership, synchronizes a local database, and serves authentication from that database. It does not call EMS3 during each authentication request. The sync entry point is `GET /v1/sync/entitlements`; it invokes asynchronous `syncAll()` and immediately returns a success DTO. The checked-in implementation contains no scheduled sync trigger. Authentication reads the locally stored function entitlements and role names using the subject from incoming user information. Sources: [DataSyncController:20](../src/main/java/com/scb/ratan/flowzero/auth/web/DataSyncController.java#L20), [EM3DataSyncService:109](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EM3DataSyncService.java#L109), [JwtConvertorForNewUse:45](../src/main/java/com/scb/ratan/flowzero/auth/jwtparser/convertor/JwtConvertorForNewUse.java#L45), [JwtConvertorForNewUse:105](../src/main/java/com/scb/ratan/flowzero/auth/jwtparser/convertor/JwtConvertorForNewUse.java#L105).

The implemented membership DTO retains only `entitlement_id`, `entitlement_name`, and `user_ids`; it drops the sample's group-level `role_entitlements`. The aggregated entitlement DTO models:

- `user_data.app_name`, `itam_id`, and `user_id`.
- `entitlements.entitlement_name` as a list of entitlement names, interpreted as local role names by this service's coordinator.
- `entitlements.role_entitlements` as `{feature, action}` pairs.
- `entitlements.data_entitlements` as `{key, values[]}` pairs.
- `data_policies.policy_rules`, `data_profiles.data_profile_rules`, and `data_entitlements_logical_indicator`.

## Synchronization and authorization behavior

1. Membership sync flattens every nonblank `user_ids` entry from the returned groups and deduplicates it. An empty aggregate skips membership reconciliation. Otherwise it compares the result to active local users. [EM3DataSyncService:35](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EM3DataSyncService.java#L35)
2. New memberships become local `ACTIVE` users; active local users absent from the returned membership set are physically deleted. This is an inferred membership lifecycle, not propagation of an EMS3 status field. [UserServiceImpl:38](../src/main/java/com/scb/ratan/flowzero/auth/service/user/impl/UserServiceImpl.java#L38), [UserServiceImpl:74](../src/main/java/com/scb/ratan/flowzero/auth/service/user/impl/UserServiceImpl.java#L74)
3. Entitlement sync iterates active database users sequentially, performs one request per user, takes response element zero, and sends its `entitlements` to the coordinator. It does not validate `user_data.user_id`, `app_name`, or `itam_id`. Empty responses throw at `get(0)` and are logged; multiple response records are ignored after the first. [EM3DataSyncService:79](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EM3DataSyncService.java#L79)
4. For each user, the coordinator transaction deletes and replaces local role records using `entitlement_name`; converts `data_entitlements` into a JSON object keyed by each `key`; and converts feature/action pairs to strings `feature:action` under the hardcoded key `Entity.flowzero_feature_action`. Repeated data keys overwrite earlier entries. Policies, profiles, and logical indicator are not consulted. [EMS3DataCoordinator:40](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataCoordinator.java#L40), [EMS3DataCoordinator:67](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataCoordinator.java#L67), [EMS3DataCoordinator:92](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataCoordinator.java#L92), [EMS3DataCoordinator:121](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataCoordinator.java#L121)
5. Empty `data_entitlements` clears stored data entitlement JSON. Empty `role_entitlements` produces `null`, but the coordinator skips writing `functionEntitlement` in that case, retaining old grants. Null `entitlements` skips the whole update. Exceptions in membership sync or individual user entitlement sync are logged and swallowed; the returned API success is an acknowledgement of starting work, not a completeness result. [EMS3DataCoordinator:121](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataCoordinator.java#L121), [EM3DataSyncService:47](../src/main/java/com/scb/ratan/flowzero/auth/service/ems3/EM3DataSyncService.java#L47), [DataSyncController:20](../src/main/java/com/scb/ratan/flowzero/auth/web/DataSyncController.java#L20)
6. Repository lookups for users and role names are cached; the checked-in Spring cache expiry is 30 seconds. The sync code does not explicitly evict these caches, so saved/deleted entitlement changes can remain invisible until cache expiry. [UserRepository:23](../src/main/java/com/scb/ratan/flowzero/auth/repository/UserRepository.java#L23), [RoleRepository:16](../src/main/java/com/scb/ratan/flowzero/auth/repository/RoleRepository.java#L16), [application.yml:39](../src/main/resources/application.yml#L39)

## Migration implications and recommendations

These recommendations follow from the observed implementation above; they are not claims that EMS3 guarantees a particular business meaning.

| Priority | Recommendation for a BFF migration | Evidence/rationale |
| --- | --- | --- |
| Required before mapping | Confirm the BFF's exact ITAM/application entitlement scope and endpoint variants with EMS3 owners. Prefer an application-scoped response or select and validate records by application, ITAM, and user identity. | The aggregate sample returns multiple applications, while the reference selects only the first record. |
| Required before deleting users | Establish full snapshot/pagination semantics, active-user lifecycle, and whether an empty result is authoritative revocation or an integration failure. | The reference deletes absent users from a nonempty response but skips an entirely empty snapshot; the payload does not model status or completeness. |
| Required for authorization parity | Preserve BFF business contracts through a dedicated mapping layer; explicitly map role names, feature/action pairs, data keys, policy/profile semantics, wildcard rules, and logical operators. | `Entity.flowzero_feature_action` is application-specific; policies/profiles and `OR` are modeled but not applied. |
| Required for revocation | Treat a successful, validated empty grant set as an explicit revocation, and clear permissions plus dependent caches atomically. Distinguish this from transport/schema failure. | Empty function grants currently retain old permissions; repository caches can retain older state. |
| Required for operational safety | Use bounded HTTP timeouts, retry only transient failures, honor expiry metadata with skew, and refresh once on a rejected bearer token. | Current retries cover every exception, cached tokens last a fixed 55 minutes, and no configured client timeouts are present. |
| Before rollout | Track sync run completeness and per-user failures, prevent overlapping reconciliation runs, and compare normalized EMS2/EMS3 output before enabling EMS3 authorization. | The current API reports initiation and catches failures; it cannot establish that every user's grants were refreshed. |

## Test evidence and limits

Existing unit tests cover token form/header construction and missing/error token responses; token caching and basic membership/entitlement fetches; user membership deduplication; and a simple coordinator save. They use mocked `RestTemplate`, repositories, and object mapper, so they do not demonstrate live response deserialization, Spring retry timing, database transaction/cache behavior, or real EMS3 connectivity. [EMS3TokenServiceTest:28](../src/test/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3TokenServiceTest.java#L28), [EMS3DataFetchServiceTest:34](../src/test/java/com/scb/ratan/flowzero/auth/service/ems3/EMS3DataFetchServiceTest.java#L34), [DataSyncControllerImplTest:21](../src/test/java/com/scb/ratan/flowzero/auth/service/ems3/impl/DataSyncControllerImplTest.java#L21), [EMS3DataCoordinatorTest:23](../src/test/java/com/scb/ratan/flowzero/auth/service/ems3/impl/EMS3DataCoordinatorTest.java#L23)

Recommended migration tests include sanitized real-shape fixtures, multiple application records and identity mismatches, empty/full/partial membership snapshots, duplicate and wildcard data keys, logical `AND`/`OR`, revoked roles/actions, 401 refresh, expiry/concurrent token acquisition, transient versus permanent failures, and cache invalidation after sync. Existing tests listed above do not cover those end-to-end contracts.
